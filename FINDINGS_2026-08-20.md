# GMX Order Flow Research — Findings
## Date: 2026-08-20

## 1. totalPendingImpactAmount

`MarketUtils.getTotalPendingImpactAmount()` reads:

`Keys.totalPendingImpactAmountKey(market)`

The value is updated through:

`MarketUtils.applyDeltaToTotalPendingImpactAmount()`

which calls:

`dataStore.applyDeltaToInt(Keys.totalPendingImpactAmountKey(market), delta)`

This means the pending impact amount is a signed `int256` tracked per market.

---

## 2. Position Impact Pool

`MarketUtils.getPositionImpactPoolAmount()` reads:

`Keys.positionImpactPoolAmountKey(market)`

`applyDeltaToPositionImpactPool()` handles negative deltas specially.

If the requested negative delta is larger than the current position impact pool:

1. Position impact pool is set to zero.
2. The excess amount is added to:
   `lentPositionImpactPoolAmount(market)`

This creates an important accounting relationship between the position impact pool and the lent position impact pool.

---

## 3. Positive Price Impact Cap

`PositionUtils.getExecutionPriceForIncrease()` first calls:

`MarketUtils.capPositiveImpactUsdByMaxPositionImpact(...)`

Positive price impact is capped using:

`maxPriceImpactFactor`

The maximum positive impact is:

`sizeDeltaUsd * maxPriceImpactFactor`

via:

`Precision.applyFactor(...)`

---

## 4. priceImpactUsd → priceImpactAmount

In `PositionUtils.sol`:

For positive price impact:

`priceImpactAmount = priceImpactUsd / indexTokenPrice.max`

The code explicitly states that `indexTokenPrice.max` is used and division is rounded down to minimize the impact amount.

For negative price impact:

`priceImpactAmount = Calc.roundUpMagnitudeDivision(priceImpactUsd, indexTokenPrice.min)`

The code explicitly uses `indexTokenPrice.min` and rounds up the magnitude to maximize the impact amount.

---

## 5. Effect on sizeDeltaInTokens

For LONG:

`sizeDeltaInTokens = baseSizeDeltaInTokens + priceImpactAmount`

For SHORT:

`sizeDeltaInTokens = baseSizeDeltaInTokens - priceImpactAmount`

If the resulting value is negative:

`Errors.PriceImpactLargerThanOrderSize(...)`

is reverted.

---

## 6. Example from GMX code

The code gives:

- price = $2000
- sizeDeltaUsd = $5000
- priceImpactUsd = -$1000

Then:

`priceImpactAmount = -1000 / 2000 = -0.5`

`baseSizeDeltaInTokens = 5000 / 2000 = 2.5`

For a LONG:

`sizeDeltaInTokens = 2.5 - 0.5 = 2`

Then:

`executionPrice = 5000 / 2 = $2500`

This demonstrates that negative price impact changes the effective token amount and therefore the execution price.

with:

- `sizeDeltaUsd`
- calculated `sizeDeltaInTokens`
- `acceptablePrice`
- long/short direction

`PositionPricingUtils.getPriceImpactUsd(...)`

`-sizeDeltaUsd`

`-sizeDeltaInTokens`

The decrease path then needs to be followed completely to determine:

- how positive/negative impact is converted to execution price

- whether long/short directions create any accounting mismatch

## 9. IncreasePositionUtils

`IncreasePositionUtils` records:

`eventParams.priceImpactUsd = cache.priceImpactUsd`

and:

`eventParams.priceImpactAmount = cache.priceImpactAmount`

The event also records `baseSizeDeltaInTokens`, while the comment notes that the event key remains unchanged for analytics.

Position fees are subsequently processed through:

`PositionPricingUtils.getPositionFees(...)`

and claimable fee amounts are updated through `FeeUtils`.

# Current Research Hypothesis

The interesting area is NOT simply the division itself.

The main question is whether the combination of:

1. asymmetric price selection (`min` / `max`)
2. asymmetric rounding
3. signed `priceImpactUsd`
4. conversion into token amounts
5. increase/decrease direction inversion
6. `totalPendingImpactAmount`
7. position impact pool / lent impact pool

can produce an accounting invariant violation across a sequence such as:

`increase → decrease`

or:

`increase → partial decrease → final decrease`

The next investigation should trace the COMPLETE decrease path and compare it mathematically against the increase path.
